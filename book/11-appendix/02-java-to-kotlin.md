# Java 到 Kotlin

很多 Android 开发者并不是从零开始接触 Kotlin，而是带着多年 Java 项目经验走进现代 Android 生态。真正让人不适应的地方，通常并不是几个新关键字，而是默认判断发生了变化。过去我们习惯先把对象写成可变、把空值留给运行时兜底、把状态拆散到 setter 和工具类里；到了 Kotlin 以后，语言开始不断逼你回答另外一些问题：这个值到底允不允许为空，这个对象是不是应该天然不可变，这段逻辑是在描述状态还是在描述行为。

也正因为如此，Java 到 Kotlin 的迁移不该被理解成一次逐行语法替换。它更像一次工程表达方式的升级。本章想帮你建立的，不是“Java 对应 Kotlin 关键字速查表”，而是一套更适合 Android 项目的迁移判断：哪些 Java 经验依然应该保留，哪些习惯需要主动放下，以及怎样用渐进方式把 Kotlin 真正变成项目里的默认语言。

## 学习目标

- 理解 Java 开发者转向 Kotlin 时最常见的思维阻力。
- 理解哪些 Java 习惯在 Kotlin 中应保留，哪些应主动放下。
- 理解 Kotlin 的空安全、不可变风格和状态表达为什么更适合现代 Android。
- 学会以“渐进迁移”而不是“一次重写”的方式完成语言转型。

## 前置知识

- 已有 Java 或类 Java 语言基础。
- 已接触 Kotlin 的基本语法。

## 正文

### 1. 真正要迁移的，是默认判断而不是语法表面

很多人写 Kotlin 时之所以总带着浓重的 Java 味道，并不是因为不会写，而是因为仍然沿用旧的默认出发点。对象一写出来先用 `var`，字段一时拿不准就先可空，状态变化先靠 setter 慢慢拼，公共逻辑则继续塞进工具类或静态风格入口里。这些写法在 Java 时代可以工作，但到了 Kotlin 里，它们会不断抵消语言原本想提供的结构收益。

所以迁移的关键不是“把 `public class` 改成 `class`”，而是先意识到：Kotlin 希望你更早表达边界。可空还是不可空，可变还是不可变，数据对象还是行为对象，临时结果还是稳定状态，这些判断不再适合拖到实现后期再慢慢补。你会发现，真正让 Kotlin 代码变好的，往往不是语法更短，而是这些边界终于被提前说清楚了。

### 2. Kotlin 不是对 Java 的否定，而是对边界的强化

Java 训练出来的很多经验其实非常宝贵。清晰的类职责、稳定的接口边界、对命名和可读性的敏感度，这些都不应该在迁移时被丢掉。真正需要调整的，是过去那些为了对抗样板代码和弱类型空值约束而形成的表达惯性。Kotlin 并不是要求你忘掉 Java，而是要求你把原本依靠约定和经验维持的边界，尽量落到类型系统和对象设计里。

这也是为什么成熟的迁移通常看起来并不激进。它不是把所有旧经验清空重来，而是在保留工程感的前提下，更新表达手段。你依然需要关心模块职责、接口稳定性和命名清晰度，只是现在可以用更明确的空安全、不可变数据和更轻量的函数式表达，把这些设计直接写进代码结构里。

### 3. 空安全会迫使你重新设计 API 和状态边界

对多数 Java 开发者来说，Kotlin 最深的一次思维转换就是空安全。Java 里很多对象默认都可能是 `null`，调用方通常只能靠经验、文档或运行时异常来判断边界。Kotlin 逼你在设计时先回答：这个值是业务上允许缺失，还是只是暂时还没有准备好；如果它允许缺失，谁来承担判空责任；如果它不该为空，为什么代码里还保留成可空类型。

这件事对 Android 特别重要，因为页面状态、网络结果、数据库查询和系统回调里都充满了空值边界。只要你认真对待 `String` 和 `String?` 的区别，很多以前会拖到运行时才暴露的问题，就能提前变成接口设计问题。尤其在和 Java API、旧 SDK 或历史项目代码互操作时，平台类型和宽松空值会不断提醒你：迁移不是“把语法换掉”这么简单，而是要把那些过去模糊的契约重新讲清楚。

一个很实用的判断是，不要一看到编译器提示就急着补 `!!`。更有价值的做法，是停下来追问这个空值到底来自哪里，它是不是应该在边界层被兜住，它进入 ViewModel 或 UI state 之前能不能被整理成更稳定的模型。只要你养成这个习惯，Kotlin 的空安全就会从“麻烦的语法限制”变成“提前发现结构问题的工具”。

### 4. 不可变状态和 `data class` 会改变你组织 Android 代码的方式

Kotlin 在 Android 项目里最实际的收益之一，是它让状态建模变得更自然。过去在 Java 风格代码里，我们很容易写出一批字段、配上一组 getter 和 setter，然后让页面或控制器在不同时间点逐个修改这些属性。这样的代码虽然直观，但一旦状态开始变复杂，就很难追踪是谁在什么时候改了哪一块数据。

Kotlin 更鼓励把状态整体表达出来，再通过复制生成新状态。`data class`、默认参数和 `copy()` 组合起来，正好非常适合 ViewModel、Flow 和 Compose 这类状态驱动场景。对现代 Android 而言，这种写法的意义不只是少写模板代码，而是让状态变化从“分散的局部修改”变成“可观察的整体替换”。

```kotlin
class LegacyProfileState {
    var name: String? = null
    var bio: String? = null
    var isLoading: Boolean = false
    var errorMessage: String? = null
}

data class ProfileUiState(
    val name: String = "",
    val bio: String = "",
    val isLoading: Boolean = false,
    val errorMessage: String? = null,
)
```

上面这两个类型都能表达“个人资料页面的状态”，但它们服务的是完全不同的设计思路。前者更像一个可随时被各处修改的容器，后者则更像一个可以整体推导、整体替换、整体观察的状态快照。真实项目里，当 ViewModel 通过 `copy()` 更新 `uiState` 时，代码的可读性、调试性和测试性都会明显更稳定。

### 5. Kotlin 的表达式风格不是炫技，而是在减少样板和隐藏副作用

Java 开发者迁移时，另一个常见阻力是对表达式风格的不适应。`when`、空安全操作符、扩展函数、集合的 `map` / `filter` / `associate`，看起来像是在换一种更花哨的写法，但它们真正的价值其实很朴素：把原本埋在中间变量、条件分支和循环里的意图直接表达出来。只要使用得克制，表达式风格不是为了“写得像 Kotlin”，而是为了让代码更短的同时也更清楚。

当然，这不意味着所有地方都要追求技巧化写法。一个成熟的迁移判断是：只在确实能让意图更清楚时再用更紧凑的表达。如果一段链式调用已经让团队成员看不懂，或者一个作用域函数让接收者上下文变得模糊，那它就不是好 Kotlin。迁移的目标不是把 Java 命令式代码全部消灭，而是逐步学会在合适的位置用 Kotlin 的表达能力减少样板、压缩噪声，并把副作用留在更容易追踪的地方。

### 6. 更现实的迁移顺序，是先改最能体现收益的层

真实项目里，最不划算的做法通常是一开始就宣布“全量重写成 Kotlin”。这种计划听起来彻底，实际上风险很高，因为它同时叠加了语言迁移、架构调整、测试回归和团队协作成本。更稳妥的路径通常是让新代码优先使用 Kotlin，再从边界清晰、收益明显的区域开始推进，例如新的功能模块、ViewModel、UI state、UseCase 或者数据模型层。

这些位置之所以适合先迁移，是因为 Kotlin 的优势在这里最容易体现出来。ViewModel 和 UI state 很适合用不可变数据建模；UseCase 和 Repository 接口很适合用更紧凑的函数表达；数据模型很适合通过 `data class` 和空安全明确边界。当这些层先稳定下来以后，团队会更容易看到迁移带来的实际好处，后续再处理互操作复杂、历史包袱更重的旧 Java 区域，阻力也会小很多。

### 7. 团队迁移真正落地，要靠评审标准而不只是个人自觉

如果你在团队环境里推进 Java 到 Kotlin，光靠“大家尽量写得更 Kotlin 一点”通常不够。更有效的做法，是把迁移判断逐步变成代码评审里的稳定问题：这段代码真的需要 `var` 吗，这个字段为什么是可空，状态对象能不能合并成一份 `data class`，这次修改是不是仍然在用 setter 铺开状态，这段 Java 互操作边界是否应该在仓库层或 mapper 层先收口。

当这些问题开始稳定地出现在评审里，团队就会慢慢形成新的默认值。迁移这件事也会从“语言兴趣”变成“工程质量的一部分”。对 Android 项目来说，这一点尤其重要，因为页面状态、异步流和本地模型一旦还保留太多 Java 式表达，后面无论接 Compose、Flow 还是更现代的数据层实践，都会显得别扭。

### 8. 实践任务

可以从一段你自己最熟、但明显还带着 Java 写法习惯的 Kotlin 代码开始。目标不是把它重写成某种炫技版本，而是通过一次小范围整理，感受 Kotlin 在边界表达和状态建模上的实际收益。

1. 找一段明显“写得像 Java”的 Kotlin 代码。
2. 检查其中哪些变量其实可以改为 `val`。
3. 检查哪些对象更适合改成 `data class`。
4. 找出一段空值边界模糊的代码，重新明确可空 / 不可空设计。
5. 只重写一小段，观察可读性和状态表达是否改善。

完成以后，你应该能更清楚地区分自己是在迁移语法，还是在迁移思维。如果改完以后代码只是更短，却仍然到处依赖可变字段、setter 和模糊空值边界，那说明真正的迁移还没有开始。

自检时，可以问自己三个问题：我是否能解释为什么这段 Kotlin 以前“虽然能跑，但还是像 Java”；我是否能说清哪些字段本来就不该可空；我是否开始把状态看成整体，而不是一组零散属性。如果这些问题已经能回答得更稳，说明这次练习达到了目的。

调试时最常见的阻力不是语法报错，而是旧习惯自动回潮。只要你发现自己又在到处补 `!!`、继续写很多 setter，或者一遇到 Kotlin 集合操作就立刻退回到最原始的命令式展开，就可以提醒自己先回到“边界是否清楚、状态是否整体表达”这两个核心判断上。

### 9. 常见误区

最常见的误区，是把 Java 到 Kotlin 理解成关键字映射，于是只追求“语法能通过”，却不调整空安全、不可变数据和状态组织方式。另一个常见问题，是因为担心迁移成本，就把 Kotlin 长期写成“没有分号的 Java”，结果语言换了，项目结构却没有得到任何收益。还有一些团队会一开始就计划一次性重写全部模块，这种路线往往低估了互操作、测试和协作成本，最后反而把迁移本身做成新的维护负担。

## 小结

Java 到 Kotlin 的真正迁移，核心不在几个新语法点，而在默认思维的更新。只要空安全、不可变状态和更轻量的模型表达真正进入你的 Android 代码，Kotlin 才会从“另一门语言”变成现代 Android 的主线工具。对大多数团队和个人来说，渐进迁移、边改边学、把判断沉淀进评审标准，通常比一次性重写更现实，也更容易得到长期收益。

## 练习题

1. 概念理解题：为什么说 Java 到 Kotlin 的最大变化不是关键字，而是空安全、不可变状态和表达式风格带来的思维迁移？
2. 编码实现题：找一段明显“写得像 Java”的 Kotlin 代码，至少完成一次 `var` 到 `val`、普通类到 `data class` 或多次 setter 到一次状态替换的重构。
3. 扩展思考题：如果你的团队准备从 Java 逐步迁移到 Kotlin，你会如何安排模块优先级和迁移节奏，才能降低一次性重写的风险？
