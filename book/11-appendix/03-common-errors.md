# 常见错误

很多学习者在 Android 入门阶段最痛苦的体验，不是知识点太多，而是错误一出现就完全不知道该从哪里下手。构建失败、依赖冲突、页面白屏、权限被拒、崩溃堆栈看不懂、列表不更新、通知不弹、WorkManager 不执行，这些问题单独看都能解决，真正让人崩溃的是它们总像随机事件一样出现。

因此，这一章的目标并不是给你列一张“报错文案大全”，而是帮助你建立一种更稳定的排查顺序。框架版本会变，报错文本会变，工具窗口也会变，但“先缩小范围，再验证假设”的排查逻辑不会变。只要这套逻辑建立起来，很多原本看似随机的故障都会重新变成可解释、可处理的工程问题。

## 学习目标

- 理解 Android 常见错误更适合按层定位，而不是按文案死记。
- 学会区分构建错误、运行时错误、状态错误和系统能力错误。
- 学会建立“先缩小范围，再验证假设”的排查顺序。
- 把常见错误处理转化为可重复的方法，而不是经验运气。

## 前置知识

- 已接触构建、页面、数据层、权限、通知和后台任务。
- 已会使用基础日志、断点和 Android Studio 调试工具。

## 正文

### 1. 排查错误时，第一步不是改代码，而是先分层

很多人一遇到错误，就马上开始改配置、删缓存、重启 IDE，或者同时动好几个文件。这样做的问题不在于动作一定无效，而在于它太早引入了新的变量。更成熟的第一步通常不是修改，而是先判断问题属于哪一层。项目根本编不过，通常是构建层问题；能编过但一运行就崩，通常先看运行时错误；不崩但行为不对，往往更接近状态设计问题；权限、通知、后台任务和组件入口没有按预期工作，则更像系统能力或系统交互层问题。

只要层级判断对了，后面的排查路径通常就会快很多。你不再是在整个项目里盲搜，而是在更小的一段链路里验证最可能的原因。

### 2. 构建错误，先查版本、依赖和环境边界

当问题发生在构建期，最常见的原因通常集中在依赖版本不兼容、Gradle / AGP / Kotlin 版本组合不合适、本地环境或缓存状态异常，以及模块引用、变体或签名配置写错。构建错误最怕的，是看到一段报错文本就立刻照着搜索结果随手改配置。因为这样做很容易把“版本组合问题”“脚本书写问题”和“环境状态问题”混成一件事。

更稳妥的顺序通常是：先判断这是版本不匹配，还是本地环境不稳定，还是构建脚本本身有逻辑错误；再去做最小修改验证。只要这三类问题没分开，越修越乱就是常态。构建层的好消息是，它往往很诚实，只是信息量大。你不需要一开始看懂所有输出，只需要先找到是哪个模块、哪个任务、哪个版本组合先开始失败。

### 3. 运行时崩溃，先看“在哪一层崩了”

崩溃堆栈最容易让初学者产生压迫感，但你不需要一开始就看懂每一行。更有效的做法通常是先问：崩溃发生在页面层、数据层还是系统组件层？是空指针、状态不合法、权限问题，还是第三方库错误？它是页面一打开就崩，还是执行某个特定操作后才崩？

只要先从“上下文 + 层级”切入，堆栈就会更容易读。你不是在理解整个 Android 运行时，而是在理解某条具体路径为什么在这里失败。例如一个 `NullPointerException` 如果发生在 ViewModel 映射状态时，排查重点和它发生在权限回调里会完全不同。很多时候，真正有价值的信息不是整段堆栈，而是“第一次进入自己代码的位置在哪里”。

### 4. 不崩但不对，往往是状态和数据流问题

很多 Android bug 根本不会崩，例如列表刷新了但 UI 没更新，搜索切词后旧结果覆盖了新结果，Snackbar 因为重建页面重复弹出，或者用户明明点了完成，列表却没有变化。这类问题之所以烦人，不是因为它们更神秘，而是因为它们通常不属于语法错误，而属于状态设计错误。

排查这种问题时，最该先问的是：这份状态到底由谁持有，这次更新是从哪条链路来的，有没有多个地方同时在改同一份状态。只要开始从“状态归谁管”这个角度去看，很多“不崩但不对”的问题都会明显收缩范围。你会发现问题常常并不在某一行代码，而在于状态模型本身没有立住，比如页面和 ViewModel 同时在改同一份数据，或者一次性事件被当成稳定状态保留下来了。

### 5. 系统能力错误，更要先检查前提条件

权限不生效、通知不弹、后台任务不执行、外部 Intent 匹配不到，这类问题表面上像“系统 API 有坑”，实际上很多都来自前提条件根本没有成立。权限请求时机可能不对，通知渠道可能还没创建，后台任务可能压根不适合当前机制，Intent 的 action、data、category 可能根本没有匹配上。系统能力类问题，先检查“这项能力依赖的前提条件是否成立”，通常比先改实现细节更有效。

这也是为什么系统问题常常不能只看页面代码。它们更像跨边界问题，需要同时看 Manifest、运行时前提、系统设置、生命周期时机和当前设备环境。如果前提条件这一层没先确认，再怎么微调调用顺序都可能是在错误方向上用力。

### 6. 一个更稳的通用排查顺序

面对大多数问题时，你都可以先按同一条顺序走。先用一句话准确描述现象，再判断它发生在哪一层；然后提出两个最可能的原因，并为每个原因选择一条最省力的验证方式，例如日志、断点、Layout Inspector、Database Inspector 或配置核对；最后一次只改最小一处验证，不要同时乱动很多地方。

这条顺序最重要的价值，是避免你在没缩小范围之前就不断破坏现场。很多错误本身并不难，真正让它们难的是排查过程引入了太多新变量，最后连“到底哪一步真正解决了问题”都说不清。只要先把验证动作收小，错误就会开始重新变得可解释。

### 7. “最近改了什么”几乎总值得先回看

很多 bug 并不是凭空出现，而是最近某次改动带来的副作用。尤其在升级依赖、调整构建配置、重构页面状态、替换数据来源之后，更值得先回看最近改了什么。排查并不是侦探小说，不需要假装一切线索都未知；版本历史、最近提交和刚改过的模块，本来就是你最应该优先利用的信息。

这也是为什么成熟团队很重视“小步修改”和可回看的提交边界。改动越集中，错误越容易回溯；改动越分散，排查成本越高。对个人学习者来说，这条原则同样成立。只要你记得“最近到底动了什么”，很多问题都能比盲目全局搜索更快缩小范围。

### 8. 什么时候该怀疑环境，而不是业务代码

并不是所有问题都来自业务逻辑。有些问题更像是 Gradle 缓存异常、模拟器或真机环境状态不对、IDE 索引和构建状态不同步，或者某次依赖下载没有完整落地。成熟的排查，并不是默认“代码一定错了”，而是能区分“环境异常”和“实现异常”。

这类判断之所以重要，是因为它直接决定你下一步要不要继续改业务代码。如果问题根本来自构建缓存或设备状态，那么继续修改业务逻辑只会把排查带偏。也正因为如此，当你已经能证明业务路径逻辑基本成立，却仍然出现解释不通的行为时，就应该把环境本身重新纳入怀疑范围。

### 9. 实践任务

起点条件：

- 已有一个真实 bug，或你最近遇到过的常见错误。

步骤：

1. 用一句话准确描述问题现象。
2. 把它归类到构建、运行、状态或系统交互层。
3. 写下两个最可能原因。
4. 为每个原因选一条最省力的验证方式，例如日志、断点、Inspector 或配置核对。
5. 记录最后真正原因属于哪一层，以及下次更快定位时该先看哪里。

预期结果：

- 读者会更少陷入“哪里都改一点”的混乱排查。
- 读者应能逐渐把错误处理变成可重复方法。
- 面对新问题时也更容易知道从哪下手。

自检方式：

- 读者应能解释为什么常见错误应先分层再排查。
- 读者应能判断某个问题更像状态错误还是系统边界错误。
- 读者应能说明为什么一次只验证一个假设更有效。

调试提示：

- 一次改很多地方，最后很难知道到底哪一步真的解决了问题。
- 报错文案看不懂时，先别慌，先从层级和上下文缩小范围。
- 系统能力问题先查前提条件，往往比先改实现更有效。

### 10. 常见误区

- 一遇到错误就立刻清缓存、重装、乱改配置。
- 不分层，所有问题都按同一种方式排查。
- 一次改很多地方，导致结果不可解释。
- 只记错误文案，不建立排查逻辑。

## 小结

常见错误真正值得沉淀的，不是你记住了多少报错文本，而是你是否建立了一套稳定的缩小范围方法。只要先分层、再提假设、再验证最可能原因，很多原本看起来随机的错误，都会重新变成可解释、可处理的工程问题。

## 练习题

1. 概念理解题：为什么 Android 常见错误更适合按构建、运行、状态和系统交互四层来定位，而不是只按报错文案去搜索？
2. 编码实现题：回顾你最近遇到的一个真实问题，按“现象 -> 分层 -> 两个假设 -> 验证方式”写出一份最小排查记录。
3. 扩展思考题：如果要为团队整理一份常见错误排查清单，你会优先沉淀哪些高频问题和验证顺序，才能真正提高协作效率？
